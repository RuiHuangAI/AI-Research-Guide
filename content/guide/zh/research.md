# 科研入门Q&A

这份指南面向对 AI 和科研感兴趣、但还不清楚研究怎样开展的同学。我们希望它能帮助你建立一个基本的认识：研究在做什么，怎样进入一项工作，学习、实验和合作又是怎样联系起来的。你可能出于好奇，也可能为了保研、留学或工作而开始。这些动机都可以；亲自参与之后，进一步认识科研、判断自己是否愿意继续，也是一段研究经历的价值。

刚开始时，我们容易把科研理解成一条需要逐级获得资格的路线：先学好数学和编程，再学机器学习、深度学习，读够论文，最后才联系老师、参与课题。但学习和研究未必需要这样分开。一个具体的问题，往往会让你知道为什么要学某些知识，也让原本抽象的概念有了可以理解和验证的对象。因此，你可以从感兴趣的问题或项目出发，自顶向下地进入研究，同时由浅入深地建立基础。能开始尝试，与已经充分掌握，是两个不同的阶段。

AI 让这种进入方式变得更容易。解释概念、阅读代码、运行实验，都可以得到比过去更直接的帮助。但获得解释和结果，也更容易被误认为自己已经理解。工具完成了一次实验，你是否知道它检验了什么；一个结果不符合预期，你能否发现问题、调整解释，这些仍然需要在实践和讨论中逐渐学会。因此，科研入门既需要资料和工具，也需要接触一项工作实际怎样推进，理解研究者在其中作了哪些判断。

下面的 60 个问答，就从这些具体的问题展开。我们当初也问过基础够不够、怎样找老师、论文怎样读，以及做不顺时该怎么办。把自己的经验和认识整理出来，是希望刚开始的同学能够同时看见具体的入口和研究的大致过程，再据此探索自己的路。

## 科研概况

<a id="q1"></a>

### 1. 科研到底是在干什么？和上课、做课程项目、打比赛有什么不同？

科研可以理解为：找到值得问的问题，提出解释或解法，再把得到的新知识、做法或产品交给社区。

上课、课程项目和比赛通常已经给定了任务，你主要考虑怎样把它完成。做研究时，问题本身也需要你判断：它为什么值得问，别人回答到了哪里，你的发现又增加了什么。实验和写作都是围绕这些事情展开的。

不必给科研加上太重的滤镜。它也是一项具体的工作，你可以选择参与，再形成自己的认识。

<a id="q2"></a>

### 2. 一个做 AI 科研的人，每天具体在做什么？除了读论文、写代码，还有什么？

读论文、写代码、和学长学姐讨论，关注前沿研究、报告和 blog，也做规划、分析结果、写作和汇报。这些事情常常交织在一起：为了弄清一个实验现象去找论文，讨论之后改掉原来的方案，再用实验验证。

具体一天未必有很多成果，有时都花在排查一个错误上。科研也是日常工作，有推进、有卡住，也需要正常的休息和生活。

<a id="q3"></a>

### 3. 我为什么要尝试科研？好奇、保研、留学、找工作，这些动机可以吗？

都可以。想解决一个问题、觉得某个方向有意思，希望保研、留学或找到工作，甚至只是想知道科研究竟是什么，都能成为开始的理由。你不需要先证明自己的动机足够纯粹。

只是，不同目的会影响你怎样选择项目、投入多少时间。如果为了升学或工作，就了解目标项目、岗位实际看重什么；如果想判断自己是否喜欢研究，就给自己接触真实研究过程的机会。

一次尝试的价值，也包括你对科研有了自己的认识，知道以后还想不想做。这个答案不必在开始之前就确定。

<a id="q4"></a>

### 4. 科研的难，主要难在哪里？哪些事情是开始之前容易低估的？

难在每一步都要和具体的问题打交道。从补基础、调研、确定 idea，到把工作做扎实，再到写作和 presentation，知道这些步骤的名字，和亲自完成它们，差得很远。你可能会忙很久才发现问题没问清楚，也可能跑出了结果，却不知道它说明什么。

AI 能加速读论文、写代码和跑实验，但执行变快，并不意味着研究自然成立。你能不能看出 Agent 走偏了，在关键处提供有价值的干预，把一个现象追问下去，最终给社区带来新的知识或 insight？这些仍然需要经历、讨论和反复判断。开始之前，容易低估的就是这部分摩擦。

<a id="q5"></a>

### 5. 我怎样才能初步知道自己喜不喜欢科研？可以先试一试，再决定是否继续吗？

可以先试。参与编写指南的一位成员，最初复现 CV 小 demo、接触 [YOLO](start.md) 时，就感到很兴奋。虽然后来转向 LLM 和 Agent，那次尝试让他发现自己喜欢这个领域，愿意继续探索。

你也可以留意，动手之后还想做什么：想把应用做得更好，还是想追问它为什么有效、在哪些地方失败？接触实现、调试和实验之后，再看看自己是否仍然愿意继续。

## 科研准备

<a id="q6"></a>

### 6. 大一、大二可以做科研吗？开始得早意味着什么，晚一点又会怎样？

可以。AI 时代一个很大的变化，是我们更容易自顶向下地做事情：从感兴趣的问题和项目出发，借助工具推进，再逐步补上需要的数学、编程和模型知识。你不必按某张统一课表全部学完，等到大三做大创，才被允许接触研究。

你不需要任何人批准“现在可以做科研了”。有想弄清楚的事情，愿意投入，也愿意把遇到的基础问题认真学明白，就可以开始。自顶向下改变的是进入问题的顺序，理解仍然需要由浅入深。

早开始的好处是有更多探索和调整的时间，不必急着凭年龄给自己贴上天才的标签。晚开始也不等于失去机会，研究是可以长期做的事情。

<a id="q7"></a>

### 7. 我的学校、成绩、英语、数学或编程不够好，还能从哪里开始？

英语、数学和编程会影响你现在能读懂什么、能完成什么，但这些能力可以在做中提升。先找一个现在能接触到的问题，遇到具体障碍再补：英文读不通，就借助 AI 解释并对照原文；代码不熟悉，就从能运行的项目里逐步理解和修改。

学校和成绩会影响一些机会的获得。可以从任课老师、学长学姐或开源项目入手，了解眼下有哪些参与机会。

<a id="q8"></a>

### 8. 我是不是得先学完 Python、数学、机器学习、深度学习，才有资格联系老师？

不需要。只是请教一个具体问题，把背景、疑问和已有尝试说明白，就可以联系。

如果希望加入项目，可以介绍自己对方向的了解、已经做过的阅读或尝试，以及能投入的时间。基础暂时不足，也把缺什么、准备怎样补说清楚，方便对方判断有没有合适任务、需要怎样指导。

<a id="q9"></a>

### 9. 我没有论文、比赛、项目经历，简历几乎是空的，怎么迈出第一步？

先做出一些能够拿来交流的东西。例如，借助 AI 复现相关论文、做一个小 demo，或者写一篇把问题讲清楚的 blog。

交流时讲清为什么选它、参考了哪些工作、自己做到哪里、还有哪些疑问。简历暂时没有论文和比赛，就用这些具体尝试让对方了解你。

<a id="q10"></a>

### 10. 如果我现在只有兴趣，每周能拿出一些时间，第一个月可以具体做什么？

第一个月可以用来把兴趣落到一次实际尝试上。去 GitHub 或 Kaggle 找一个规模合适、能看到结果的项目，例如图像分类、YOLO 检测，或简单的工具调用 Agent。选哪个，主要看什么效果让你想亲手试试。

时间有限，就先围绕这个项目学：它接受什么输入，怎样得到输出，自己改动一处会发生什么。到月底，可以回看自己弄明白了哪些部分，还想继续探索什么，再决定接着做还是换个项目。

## 研究方向

<a id="q11"></a>

### 11. 我连有哪些研究方向都不知道，应该先去哪里看？

小红书、知乎、B 站、新智元等媒体，以及 [GitHub 的 awesome 系列](catalog-directions.md)，都可以作为入口。也可以让 AI 帮你解释第一次遇到的概念。

看到感兴趣的方向，再去读原论文、看看代码，了解它到底在做什么。

<a id="q12"></a>

### 12. LLM、Agent、具身、RL、World Model 这些名字，怎样才能从“听过”变成知道它们在解决什么？

从它想获得的能力、想解释的现象入手。有实际应用的方向，可以看它怎样进入生活，哪些地方仍做得不好；还没有成熟应用的，也可以看研究者试图让模型做到什么，眼下卡在哪里。

例如，一个 Agent 能演示订票，不代表它在信息变化、工具报错时仍然可靠。沿着这个差距去读论文，就能进一步看作者具体研究什么问题、为什么出现、怎样解决，以及结果支持了什么。逐渐积累这些联系，你对一个方向的认识才会超出展示效果和名称。

<a id="q13"></a>

### 13. 怎么区分“我喜欢这个方向的展示效果”和“我愿意做这里面的研究”？

做一做会清楚很多。先了解 demo 怎样实现，再接触让它成立的那些工作：处理数据、调试、分析错误、修改方案。你愿不愿意继续弄清其中的困难，比看展示时有多兴奋，更能说明你是否想做这方面的研究。

如果发现效果只在精心挑选的条件下成立，也可以继续问，换个场景为什么就失败，能不能改善。如果这些问题让你好奇，就有继续探索的理由；如果你主要喜欢最终效果，也完全可以去做应用或开发。

<a id="q14"></a>

### 14. 选方向时，兴趣、导师、资源、难度、热度和未来发展，应该怎么考虑？

我们更看重选择是否给你留下自由发展的空间：能否保持兴趣、获得有质量的讨论，遇到新问题时又能否调整。刚入门时，很难一次就找到长期最适合自己的方向，不必把选择理解成终身绑定。

具体来看，兴趣支撑持续投入；导师和合作者影响日常怎样推进、卡住时有没有反馈；数据、算力和硬件决定想法能否试起来。难度要结合自己的基础和支持条件看，热度则既可能带来资料与机会，也可能意味着竞争快、问题很快被解决。

这些条件很难全部满足。优先考虑眼下有兴趣、有人支持、资源足以动手的选择，同时留意自己能否在其中学到可迁移的知识和能力。对未来的判断会变，继续学习和调整的能力值得保留。

<a id="q15"></a>

### 15. 为什么要看校外、其他实验室和公司的工作？看论文、项目、演讲、开源代码时，具体看什么才有用？

只看自己组里的任务，容易知道眼前该做什么，却不知道它在整个领域里处于什么位置。看其他实验室和公司的工作，是为了逐渐理解大家为什么研究这些问题，认可什么思路，前沿的热点和卡点在哪里。

具体可以沿着变化看：原来的做法满足不了什么需求，新的方法解决了哪一部分，又留下什么 gap。论文、项目、演讲和代码从不同侧面呈现这些信息。它们联系起来，你才更容易判断一个想法是在重复已有工作、补一个局部缺口，还是可能改变大家看待问题的方式，也更清楚自己能给社区增加什么。

## 联系老师与学长

<a id="q16"></a>

### 16. 我可以主动联系不认识的学长、老师吗？可以跨学院、跨学校，甚至联系海外的人吗？

可以，跨学院、跨学校或联系海外研究者也都可以尝试。先了解对方的工作，并想清楚为什么联系：是读论文遇到一个问题，想交流某个方向，还是希望参与项目？有具体来意，才容易开始有内容的交流。

共同认识的人可以帮忙介绍，社群、小红书和 cold email 也都是入口。但认识人本身不必成为一个独立任务。共同的问题、一次有共鸣的讨论，往往才是以后继续联系或合作的基础。

<a id="q17"></a>

### 17. 从哪里找到这些人？怎么知道他的工作和我有关，也可能愿意指导本科生？

可以从你感兴趣的论文作者找起，沿着主页、Google Scholar 和合作者继续了解；学校与实验室官网、AgentHub、科研交流群和小红书，也会有成员介绍与招募信息。

判断是否相关，主要看对方最近在研究什么，与你想了解的问题有没有交集。判断能否指导本科生，可以看有没有本科生成员、学生项目或公开招募；作者名单本身未必能看出年级，最好结合成员主页。

即使没有招募，也可以礼貌地发消息询问。愿意回答问题和有时间带项目是两回事，具体有没有合适任务，需要交流后才知道。

<a id="q18"></a>

### 18. 第一次联系时，我可以提出什么请求：问一个问题、约一次交流、旁听组会，还是直接问有没有项目？

这些请求都可以，关键是把这次联系想解决什么说清楚。读论文遇到疑问，就说明具体卡在哪里；想了解一个组，可以询问是否方便交流或旁听；希望参与项目，也可以直接问有没有合适任务。

我们通常会先约一次交流，聊对方在做什么、你想参与什么，以及双方的时间和安排。

<a id="q19"></a>

### 19. 第一条消息或邮件具体写什么？没有漂亮履历，怎样说明自己的情况和来意？

介绍你是谁、为什么联系、对什么工作感兴趣，以及希望请教什么或参与什么。简历可以附上；经历少，就用已有的阅读、代码或项目说明自己的情况，不必把普通经历包装得很大。

例如：“我是××专业的大二学生，读了您关于××的工作，对其中的××问题很感兴趣。我尝试复现了××，目前做到××，希望了解是否有适合本科生参与的任务，每周可以投入××时间。”

漂亮履历并不是唯一能提供的信息。能说清自己的尝试、具备基本的执行能力，也能帮助对方判断从哪里开始合作。

<a id="q20"></a>

### 20. 发出去之后通常可能发生什么？没回复、被拒绝、被问住了，我该怎么办？

可能没有回复，可能婉拒，也可能加微信继续聊、安排读论文或试做。初次交流的要求因人而异，很多时候，双方首先在了解：项目能怎样带你，你能做什么，你又希望得到什么。

没回复，可以隔一段时间礼貌跟进一次。被拒绝了也正常，看看对方有没有指出能改进的地方，再联系其他合适的老师或学长学姐。被问住了，就照实说自己理解到哪里、还缺什么，之后再补。

## 课题组与指导关系

<a id="q21"></a>

### 21. 老师说“可以聊聊”，第一次见面会聊什么，我需要准备什么？

通常会聊你对方向的了解、做过什么、想参与什么，有时也会问基础知识。可以准备简短的自我介绍，选一两项自己熟悉的阅读或尝试，讲清楚问题、做法和自己的理解。

这次见面也是你了解合作的机会：谁会实际指导，眼下的任务是什么，预期投入多少时间，你希望得到的学习和支持能否实现。

<a id="q22"></a>

### 22. 对方发给我一篇论文，让我“先看看”，到底希望我做到什么程度？

“先看看”可能是让你了解背景，也可能是为汇报或复现做准备，最好先确认期待和下次讨论时间。目标不同，需要读到的程度也不同。

如果是初步交流，至少讲清论文研究什么问题、为什么这样做、主要方法和证据是什么，以及自己还有哪些疑问。如果接下来要参与这个课题，就还需要了解它在相关工作里的位置，进入实现和实验细节，看看哪些地方可以分析或改进。

再往外，和其他领域的相似问题建立联系也很有价值，但不必把所有层次都当成第一次读完就要完成的要求。

<a id="q23"></a>

### 23. 我能不能先了解项目、旁听或试做，再决定加入？要提前问清楚哪些事情？

可以先了解项目，询问有没有旁听、短期试做或阶段任务。试做的意义，是让双方接触实际工作，再判断合作是否合适。

开始前就把这段时间做什么、由谁反馈、预计投入多少，以及需要什么资源聊清楚。涉及成果使用和署名，也可以先了解讨论原则；具体贡献发生变化时再调整。不要等投入了很久，才发现双方对这段合作的理解完全不同。

<a id="q24"></a>

### 24. 怎么了解谁会实际带我、多久交流一次、需要投入多少时间，以及有没有数据和算力？

直接问具体安排。很多项目由组里的博士生、硕士生实际指导，老师参与的频率也各不相同。

可以问：“平时主要和谁讨论？多久同步一次？卡住时找谁？目前能用哪些数据和算力？这项任务大致需要怎样的时间投入？”也把自己的课业和每周可投入时间说明白，和对方确认现有安排下任务能否推进。

<a id="q25"></a>

### 25. 我怎么判断一段指导关系是否适合自己？如果长期得不到反馈，或觉得安排不合理，可以怎么沟通、换组或退出？

看这段合作是否给了你实际需要的支持：任务是否清楚，遇到问题能否得到反馈，投入与预期是否匹配，做的内容是否仍是你想参与的。觉得不合适时，可以先和直接带你的学长学姐或老师聊具体的问题，看看能否调整。

有些合作确实会渐渐减少联系，双方也慢慢知道这段合作不会继续。还没形成具体任务时，这可能就是一种自然的结束；如果已经有人在等你的结果，就需要把进度、代码和未完成的事情交代清楚，方便对方安排后续。

你也可以在了解其他机会后，和直接指导你的人沟通退出。一次合作结束，不一定影响以后正常交流，适合的时候仍然可以再合作。

## 基础知识与学习

<a id="q26"></a>

### 26. 做 AI 科研需要哪些共同基础？不同方向的要求又有什么区别？

共同基础主要是数学、编程、机器学习与深度学习，以及让实验运行起来的计算机系统知识。数学里，线性代数、微积分、概率统计、优化和信息论，会在不同问题中反复用到；infra 则涉及环境、数据处理、训练、评测和算力使用。

不同方向会更依赖其中一些部分。例如，强化学习的策略梯度涉及怎样用采样估计期望和梯度，概率统计会直接影响你对估计过程的理解；CNN、Transformer 中的卷积、线性映射和注意力计算，则需要线性代数与张量运算的知识。真正[训练模型](llm.md)时，还要理解数据怎样组织、显存用在哪里、计算怎样执行，才能排查运行问题。

可以从问题出发逐步建立这些基础，理解时仍然需要由浅入深。公式、实现和实验联系起来，才更容易知道一个做法为什么有效。

<a id="q27"></a>

### 27. 学课程、读书、做项目，怎么搭配？我怎样避免一直准备，却迟迟没有开始？

围绕自己想弄明白的东西搭配。项目会暴露具体的问题，课程和书本能帮助你把这些问题背后的知识学得连贯；读 blog、看代码或请教别人，也可能让某个细节突然清楚。哪种材料有用，要看它是否解释了你卡住的地方。

做研究可以自顶向下，基础理解仍然需要由浅入深。可以先学到不妨碍当前理解和推进的程度，再针对这个方向系统补充，而不是不断换入门课，等一个“准备齐全”的时刻。已经有想试的项目，就让阅读和动手同时发生，具体的困难会告诉你还缺什么。

<a id="q28"></a>

### 28. 遇到一个不懂的概念，什么时候应该停下来系统补课，什么时候可以先了解大意？

先看你现在需要用它做什么。如果它直接影响当前的计算、实现或结果解释，就值得停下来认真学；如果只是背景中的一个分支，可以先了解大意，把主要思路接起来。

需要反复使用的概念，迟早要建立更完整的理解。比如第一次遇到 KL 散度，可以先知道它在这篇文章中承担什么作用；当你开始研究约束怎样影响策略更新时，就不能停在一句定义上。先后顺序可以灵活，理解的缺口要随着实际需要逐步补上。

<a id="q29"></a>

### 29. 看过课程、能跟着代码跑，和真正掌握之间，还差什么？怎样检验自己会不会？

相比 AI 普及以前，我们学习知识、理解代码和运行实验的成本低了很多。这既是优势，也容易带来误判：AI 解释得很顺，demo 也跑通了，我们便把“听懂解释、看到结果”当成了自己已经掌握。

关键在于，**学习不能掉信息量**。比如，听到“[TRPO](rl.md) 约束策略更新，PPO 可以使用裁剪目标，GRPO 利用同一问题多次采样的组内相对奖励估计优势”，你得到了一层概括。继续往下，策略如何采样，优势怎样估计，目标和约束如何影响更新，又在哪些条件下有效或失效，才是更具体的理解。推公式、读实现和实际实验，能让你把这些关系逐步联系起来。

检验时，可以拿一次实际运行来讲：数据怎样进入程序，目标怎样计算，为什么选这些设置；改动一处之后，你预期会发生什么，结果是否符合预期。解释不清、预期落空的地方，就是值得继续追的缺口。

这样的检验是为了找到需要深入的地方，不必凭能否手推公式给自己判定“配不配做研究”。沿着问题复现、改动、讨论，看到它怎样运行、又怎样失败，才能逐渐有自己的观察。

相关资料：[TRPO 原论文](https://arxiv.org/abs/1502.05477) · [PPO 原论文](https://arxiv.org/abs/1707.06347) · [DeepSeekMath：GRPO](https://arxiv.org/abs/2402.03300)

<a id="q30"></a>

### 30. 在 AI 能解释概念、写代码的情况下，哪些基础仍值得自己花时间建立？

经常用到的数学、模型原理、计算机系统和实验方法，值得自己逐渐掌握。这样讨论或实验出现问题时，你能先判断卡在哪一部分，向 AI 或合作者提出具体的问题，不必每次都从头等待解释。基础内容可以结合[第 26 问](#q26)看，深度则随实际工作继续补。

研究也需要表达、合作和组织能力。讲清一项工作、回应质疑、协调任务和推进讨论，都会影响合作。也要主动走出去，讲自己的工作和想法，让别人认识你的问题意识和实际经验。

## 论文检索与阅读

<a id="q31"></a>

### 31. 第一次读论文应该选什么？经典论文、综述、最新论文、老师指定的论文，分别怎么用？

先看这次为什么读。想知道论文怎样呈现一项研究，可以选一篇有成熟讲解的经典工作；想进入一个方向，可以用综述建立大致的关系，再去读其中最相关的原论文；已经有具体任务，就从老师指定或直接相关的文章开始。最新论文适合了解前沿正在推进什么，但通常需要更多背景。

比如对 Agent 感兴趣，可以让 AI 帮你梳理：LLM 原有能力有什么不足，思维链提示试图改善什么，[ReAct](https://react-lm.github.io/) 怎样把推理与行动、环境反馈结合起来，再根据兴趣去看多 Agent 或 Agent RL。这里要串起的是问题与做法的联系，而不只是记住一串名字。

相关资料：[ReAct 原论文](https://arxiv.org/abs/2210.03629)

<a id="q32"></a>

### 32. 一篇论文打开之后先看哪里？第一次读完，至少应该能回答哪几个问题？

可以参考李沐老师读论文的思路，先看摘要、引言、关键图和结论，弄清作者声称做了什么、为什么做，再进入方法和实验，检查它怎样实现、证据是否支持结论。

第一次读完，至少能够用自己的话讲清问题、主要做法和结果，并知道哪些地方还没懂。任务、数据集、baseline 和指标，也要放在这个过程中理解：它们共同决定这篇文章究竟验证了什么。

<a id="q33"></a>

### 33. 英文、公式、术语和背景都看不懂，怎么办？哪些可以暂时跳过？

可以让 AI 带着读，解释句子、术语和背景，也可以参考作者报告、视频、blog 和论文笔记。读不懂时，先辨认是语言没读通，还是句子读通了、背后的概念却不熟悉，两种困难需要补的东西不同。

公式也有层次：先弄清各个量是什么、这一步想计算什么，再进入推导。和当前问题关系较远的推导可以暂时略过；如果公式正是你要实现或修改的部分，就需要具体拆开。讲解帮助你进入原文，关键定义和条件还要回原文确认。

<a id="q34"></a>

### 34. 什么叫“读懂一篇论文”？需要理解每个推导、读完代码、复现结果吗？

“读懂”有不同深度，要和阅读目的对应。为了了解一项工作，能够讲清它的问题、主要方法、结果和局限，已经是有用的理解；为了复现、分析或改进，就需要进入相关推导、代码和实验设置。

推公式、读实现、复现结果，会增加你接触到的信息，也可能改变第一遍的认识。但并非每篇文章都值得你投入同样深度。要紧的是知道自己目前理解到了哪里，哪些判断还没有实际核实。

<a id="q35"></a>

### 35. 读完以后怎么留下有用的东西？怎么把几篇论文联系起来，而不是各记一份摘要？

飞书、Notion、[Zotero、Obsidian](irene-workflow.md#notes) 都可以，工具顺手就好。真正值得留下的，是你对问题的理解、没想通的地方，以及它和已有工作的联系；AI 生成的摘要可以辅助整理，但不能替代这些内容。

几篇文章放在一起时，可以围绕同一个问题看：为什么前一种方法还不够，后一篇改变了什么，比较条件是否相同，结果又留下什么疑问。时间、引用关系和方法相似性都是线索，但最后要说清它们在问题上有什么联系。这样积累下来的，才不只是几份彼此独立的摘要。

## 研究问题与选题

<a id="q36"></a>

### 36. 刚入门的人需要自己想 idea 吗？跟着别人做一个已有课题，能学到什么？

不必先独立想出一个好 idea，才有资格参与研究。想法常常是在阅读、使用工具、观察结果和讨论里逐渐形成的，也可能来自一个已经明确、但还没有解决好的目标。

跟着做已有课题，可以完整地看一项工作怎样推进：问题怎样确定，实验怎样检查，失败后怎样调整，文章怎样组织，合作者怎样分工。参与时弄清自己负责的部分为什么需要做，它怎样影响整个项目，比只接到一个任务、跑完就结束，更容易让你以后独立推进工作。

<a id="q37"></a>

### 37. 研究方向、研究问题、idea、方法，这几个东西有什么区别？

研究方向是一片领域，比如 Agent、具身智能、世界模型，回答你大致在哪里做研究。研究问题是其中一个具体疑问，比如“Agent 做长任务时，为什么越到后面越容易出错”。

idea 是你对原因或解法的猜测，例如怀疑早期错误没有被及时发现，后续行动又不断依赖这些错误。方法则把这个想法变成可实现的设计：怎样检查、何时触发、怎样纠正。实验再检验这套做法是否解决了原来的问题。

只说“做 Agent”，还没有说出研究问题；直接加一个检查模块，也还需要解释它为什么应该有用。把问题和想法讲清楚，后面的设计才有依据。

<a id="q38"></a>

### 38. 为什么别人读论文能发现问题，我读完只觉得“做得真好”？

经验和背景知识会影响你读得到什么。对一个领域更熟悉的人，知道已有方法在哪些条件下失败，也更容易留意论文中的假设、比较和遗漏。你暂时看不出来，不必靠强行挑毛病证明自己读懂了。

可以和有经验的人读同一篇文章，问他为什么注意到某个细节、依据是什么。自己觉得好奇或不确定的地方，也可以查后续工作、看实现或做实验。提出一个具体问题并追下去，就是开始形成判断的过程。

<a id="q39"></a>

### 39. 有了一个想法，怎么判断别人是否做过、它有没有意义，以及自己能不能做？

先调研相近工作，比较它们研究的条件、动机和做法细节。只凭关键词相似，容易把不同问题当成重复；只换了一个名字，也不代表已有工作没做过。

意义可以分开看。一个问题让你好奇，就值得你花些时间探索；如果希望成为可以交流的研究成果，还要问它能给别人增加什么：新的知识、解释，还是已有方法没有提供的能力。

能不能做，则要落到验证上：需要哪些数据、算力、工具和时间，你或合作者能否获得？motivation 支撑投入，小规模尝试可以帮助你摸清实际条件。

<a id="q40"></a>

### 40. 怎样判断一个问题值得继续投入？发现有人做过，或者初步尝试没效果，就应该放弃吗？

发现有人做过，先看他回答了多少、条件与你是否相同、还有什么没解释。如果问题已经被充分解决，就重新判断自己还能增加什么；领域公认走不通的做法，也值得先了解原因，再决定是否重试。

初步尝试没效果时，先区分实现出了问题，还是想法在这些条件下没有得到支持。失败的条件、原因和适用范围，也可能是值得分析的研究内容。但若只是重复一个已经明确的结论，就需要改变问题或做法。

## 实验与结果分析

<a id="q41"></a>

### 41. 拿到一个课题之后，怎样把“做研究”拆成今天、这周能执行的事情？

从最后想回答的问题往回拆。你准备提出什么主张，需要哪些证据，什么实验能提供这些证据，又依赖哪些数据、baseline 和评测？这样才知道眼下的任务为什么要做。

刚接触课题时，通常需要读最相关的几篇文章、跑通参照、弄清数据和指标。之后把任务写到能动手的程度，例如“检查这类错误是否主要发生在长任务后半段”，而不是只写“继续优化 Agent”。一周的结果应当帮助你判断原来的猜测，或者明确下一步还缺什么证据。

<a id="q42"></a>

### 42. 为什么要跑 baseline、复现已有工作？跑通了代码之后，还要检查什么？

baseline 是比较的参照。你说改动带来了提升，需要知道相对什么、在什么条件下提升；[复现](reading.md#paper-code)也会让论文里的数据、训练和评测细节变成你真正接触过的东西。

跑通之后，检查结果与论文差多少，数据划分、配置和评测是否一致，有没有泄漏，再看不同随机种子下的波动。最后一定打开具体输出：一个总分可能掩盖明显错误。若直接采用已有结果作参照，也要确认比较条件，不能把不同设置下的数字当成同一场实验。

<a id="q43"></a>

### 43. 一个实验开始之前，应该明确什么？怎样避免不断跑实验，却不知道自己在验证什么？

先想清楚这次实验验证什么、预期看到什么，以及不同结果分别支持或削弱哪种解释。如果这次实验既无法区分不同解释，也不会提供新的信息，就应该重新考虑有没有必要跑。

想判断一个因素的作用时，尽量保持其他条件一致，并记录改动。先用小规模检查流程，再投入完整实验；需要研究因素之间的相互作用时，则按这个目的设计组合。

<a id="q44"></a>

### 44. 指标涨了就说明 idea 有效吗？怎样排查实现错误、不公平比较、偶然波动等问题？

指标提升是一个现象，还需要查清它从哪里来。先检查实现和评测：有没有数据泄漏、测试集调参或计算错误；再看比较条件，包括数据、资源、配置和调参投入是否合理。

多次运行可以了解随机种子变化带来的波动。当提升幅度与不同随机种子之间的波动接近，或比它更小时，不能仅凭一次结果断言有效，也不能直接判成“等于没涨”；需要结合重复实验和合适的统计分析判断证据。

消融和具体样本分析则帮助你检查原因。去掉新模块后是否变化，变化发生在哪些样本上，是否符合提出方法时的解释？这些检查用来判断，提升能否归因于你提出的做法。

<a id="q45"></a>

### 45. 实验失败、复现不出来、连续几周没进展时，怎么定位问题，什么时候应该求助或调整方向？

先把“不对”缩到能检查的环节：数据是否正确，输入输出是否符合预期，关键计算有没有问题，评测与预定设置是否一致。用少量样本、简单设置或已知结果排查，比一直重跑完整实验更容易定位。已经没有新线索时，就把条件、现象和试过的办法整理好，找学长学姐或原作者请教，不必耗到连续几周才开口。

复现不出来时，检查实际设置与论文的差异。如果关键细节始终无法确认，就和合作者讨论是否继续排查，或者换一个能够核实的参照。

如果流程已经确认可靠，结果却持续不支持自己的猜测，就回到假设本身，检查还有哪些解释需要验证。

## 交流与合作

<a id="q46"></a>

### 46. 卡住多久应该问人？提问之前需要尝试什么，又怎样避免为了“不麻烦别人”一直耗着？

自己试了半天到一天，已经没有新思路，就可以问，不必硬耗到一周。这个时间只是参照：如果问题会阻塞合作或消耗大量资源，更应该及时同步。

提问前先搜索、看文档、检查报错，也可以问 AI，把现象和已经试过的办法整理好。有经验的人可能一句话就发现你漏掉的条件。合作里，及时把问题说清楚，往往比为了“不麻烦别人”一直没有进展更方便大家安排工作。

<a id="q47"></a>

### 47. 向学长或老师请教时，怎样把问题讲清楚，让对方能帮上忙？

讲清四件事：我想做什么，已经试了什么，现在看到什么现象，我猜原因是什么。附上能帮助判断的关键代码、日志、报错或结果，并说明必要的运行条件。

材料够用就好。能定位到一段代码或一组样本，就不要让对方先翻整个项目；如果不确定问题在哪，也把排查过的范围说清楚。

<a id="q48"></a>

### 48. 周会、组会、进度汇报到底汇报什么？没有正结果时，还能汇报什么？

汇报这段时间做了什么、得到什么认识、接下来打算做什么。没有正结果，也可以讲试了哪些方案，出现什么现象，排除了哪些可能，现在卡在哪里、需要什么帮助。

负结果有价值，前提是把条件和证据讲清楚。还没有查明原因，就把它作为待解释的现象，不必硬编一个结论。最不利于合作的是因为没有漂亮结果就不说话，让别人既不了解进度，也不知道怎样帮忙。

<a id="q49"></a>

### 49. 听不懂讨论，或者觉得老师、学长说的可能不对，可以怎样追问和提出不同看法？

听不懂可以当场问，也可以记下来会后问。“这个词我还不熟悉，能结合这里的例子解释一下吗？”就能让对方知道你卡在哪里。

觉得结论可能不对时，把自己的理解和证据摆出来，例如：“如果按这个解释，我预期会看到 A，但实验得到 B，这里是不是还漏了一个条件？”老师和学长学姐也会出错，可以一起检查。

<a id="q50"></a>

### 50. 合作时，任务、贡献、署名和时间预期应该什么时候讨论？遇到分歧怎么办？

最好开始合作时就谈：谁负责什么，大致投入多少时间，目标是什么，署名准备怎样根据贡献讨论。贡献和任务中途变化很常见，变了就及时再谈，避免双方一直按不同的预期做事。

有分歧先和当事人直接沟通，说明各自承担的工作和理解；解决不了，再找共同的指导者协调。重要约定可以留下书面记录。刚开始开口可能有些尴尬，但比临近投稿才发现彼此期待不同，更容易处理。

## 科研中的 AI 使用

<a id="q51"></a>

### 51. 读论文、写代码、做实验、找 idea、写作，分别可以怎样借助 AI？

读论文：让 AI 解释句子、公式和背景，梳理相关工作的联系，再带着疑问回原文核实。

写代码：搭框架、写脚本、查报错都可以交给它，也可以结合论文，让它带你沿数据流理解实现；核心计算和评测要确认与研究设定一致。

做实验：讨论实验设计，执行任务、整理记录、作图和分析异常。需要关注的是，这些实验究竟在检验什么，输出是否支持解释。

找 idea：拿自己的问题和想法与它讨论，查相近工作、考虑其他解释、找方案里的漏洞。对话可以帮助打开思路，具体是否有人做过还要回到原始工作核对。

写作：讨论主线、调整结构和表达，追问每段想传达什么、为什么放在这里。文章的主张仍然要落在自己的研究和证据上。

<a id="q52"></a>

### 52. AI 给了一个听起来很合理的解释、方案或结果，我怎么判断它是否可信？

先要它拿出支撑这句话的东西。说实验成功了，就看配置、原始日志、输出和统计；说论文得出了某个结论，就找对应原文，检查条件是否一致。不要只接受“整体表现很好”一类概括。

数据和记录还要能互相对应。总分有没有算错，具体样本是不是它描述的样子，有没有只挑成功的部分？方案听起来合理，也只是值得尝试的理由，仍需设计实验区分不同解释。遇到反例时先保留问题，不急着再让 AI 给出一个圆满说法。

<a id="q53"></a>

### 53. 同样是让 AI 完成任务，自己理解其中的方案、指标、基础和 trick，实际会带来什么差别？

区别会在合作和条件变化时显出来。别人问为什么这样设计、指标在测什么、某个 trick 为什么需要，你能不能结合实际过程讲清楚？数据换了、实验出了意外，你能不能判断原来的方案还适不适用？

这些问题不能每次都靠重新问一遍 AI 才能回应。即使代码和实验主要由 AI 完成，你也需要能够参与讨论，解释当前的结果，并和合作者决定下一步。

<a id="q54"></a>

### 54. 怎样把一次借助 AI 完成的任务，变成自己的经验和直觉？怎么发现自己只是跟着它走？

做完后，选一次自己实际参与的决定回看：当时根据什么选方案，预期什么结果，后来哪里不符合预期、为什么改了做法。下一次遇到类似问题，可以用这段经历判断先查哪里。

例如，借助 AI 写论文时，如果发现某个结论缺少实验支撑，就需要补实验，或收窄原来的说法。弄明白这次修改为什么必要，下次写作时也更容易发现类似缺口。

如果每个选择都只能解释成“AI 建议的”，就从其中一个关键决定往回追，看看依据、替代方案和实际结果。

<a id="q55"></a>

### 55. 哪些材料可以交给 AI，哪些需要先确认权限？论文里使用 AI 时，需要注意什么规范？

公开论文、开源代码和自己的笔记，通常比较容易用于 AI 辅助处理。组里尚未发表的 idea、数据和草稿，别人提供的非公开代码，以及涉及隐私或保密约定的材料，则要先确认使用权限和所用服务的数据处理政策。

审稿要单独看当年的会议规定，不能因为自己平时这样用 AI，就把待审稿件交进去。例如 [ICML 2026](https://icml.cc/Conferences/2026/LLM-Policy) 区分禁止使用和允许有限辅助的两种政策，允许辅助也不等于允许把评判交给 AI。

写论文时，同样查目标会议或期刊对 AI 使用和声明的要求。作者需要对内容承担责任，AI 不能替你承担作者责任；参考文献、数据和每项论断都要核实，不能因为工具生成得像真的就直接写进文章。

相关资料：[ICML 2026 投稿规定](https://icml.cc/Conferences/2026/CallForPapers)

## 论文与研究成果

<a id="q56"></a>

### 56. 一项工作做到什么程度，才适合开始写论文？写作在研究过程中起什么作用？

不必等全部实验结束才开始写。先整理问题、方法和已有结果，往往能发现哪里还讲不清、缺什么证据，也帮助你安排后续实验。写作既传达研究，也让你检查研究是否已经想清楚。

至于什么时候能形成一篇完整论文，要看观点和做法是否有与之相称的证据：实验支持了什么，分析解释了什么，哪些条件下成立。solid 首先是主张站得住，实验的数量由需要回答的问题决定。

<a id="q57"></a>

### 57. 什么是好的研究、好的论文？有新方法、指标更高、发在好会议，分别能说明什么？

我们更看重一项工作给社区增加了什么：新的知识或 insight，更好的方法，或者对原来问题的重新理解。新方法是一种贡献形式，指标提升是一种信号，还需要看它在什么条件下发生、是否真的解决了有意义的问题。

发表在好会议或期刊，说明工作通过了相应的评审，也有助于传播和交流。但评价具体研究时，仍要读它的问题、方法和证据，不能只凭发表渠道判断。涉及升学或成果认定，则查学校和项目的具体要求。

<a id="q58"></a>

### 58. SCI、CCF A 类会议、顶会、workshop、预印本分别是什么？本科生应该怎样理解这些评价和发表渠道？

SCI／SCIE 是科学文献索引体系，日常说的“SCI 期刊”与其收录有关。期刊分区是另一套评价，讨论时要分清收录、分区及所用的分区体系。

CCF A 类来自中国计算机学会的推荐目录，目录把相关会议和期刊分为 A、B、C 类。它是推荐列表，具体用于保研、评奖或毕业时，仍要查学校和项目的认定规则。

“顶会”是领域内对重要会议的习惯称呼，例如 NeurIPS、ICML、ICLR、CVPR、ACL，涉及的研究方向不同。领域口碑与 CCF 分类也不完全等同。

Workshop 是围绕某个主题组织的研讨交流，常与大型会议同期举办。是否正式归档、接受什么工作、以后能否扩展再投，要看具体规则，不能一概理解为门槛低的正会练习。

预印本是较早公开传播的论文版本，arXiv 是常见平台。上传本身不代表通过同行评审；同一篇文章之后可能正式发表，阅读时要看版本和发表信息。

<a id="q59"></a>

### 59. 第一段研究没有论文、投稿被拒，怎样判断这段时间有没有价值？我可以用什么具体变化观察自己的进步？

可以把这份问题清单从头看一遍：哪些问题当初只能问别人，现在已经自己经历过，知道怎样理解和处理了？

例如，读一篇新论文，是否更容易看出它在回答什么、证据是否充分；遇到报错，是否知道从哪里查；听组会，能否跟上讨论并提出问题；对一个方向，是否有了自己的认识和想继续探索的事情。

被拒稿后，可以再对照审稿意见检查工作：哪些批评有依据，哪些地方需要补实验或改写，哪些分歧需要用证据说明。

<a id="q60"></a>

### 60. 一个项目推进不下去时，怎么判断该继续、调整方向，还是暂时停下来？

先分清项目卡在哪里：是实现或评测还没查清，假设没有得到支持，还是数据、算力、时间和协作条件已经不足？

实现问题仍有明确的排查办法，就约定下一阶段要检查什么、投入多少时间；问题太大或资源不够，可以缩小范围，先验证其中能做的一部分。若多次检查后，证据仍不支持原来的假设，就重新讨论解释或研究问题，而不是只靠增加实验次数继续推进。

决定暂时停止时，把已经完成的实验、代码、结论和未解决的问题交接清楚，并和合作者说明后续安排。
